# 10 — Модель географии, помещений и панелей

Статус: 🟡 черновик · 2026-09-29

Уточнение к [[09 - план изменений прототипа настроек SIP]], §1.3 «Левое меню: география».
В плане сказано, что делать (гибкая глубина адреса, необязательные подъезд и этаж,
«помещение» вместо «квартиры»), но не сказано, по каким правилам. Этот документ закрывает
модель: какие уровни есть, какие обязательны, где живёт ЖК, к чему крепится вызывная
панель и что меняется, когда продукт поедет за пределы РФ.

Продукт сначала поставляется в РФ, потом в другие страны. Поэтому граница «общее ядро /
национальная часть» заложена сразу — переделывать её потом дороже, чем провести сейчас.

Относительно плана 09 документ уточняет два его вердикта:

- ❌ «ЖК остаётся уровнем иерархии» → ЖК убирается из иерархии, но сохраняется как
  сущность (решение 6);
- ссылка адресных узлов на реестр и режим «нет в реестре» переезжают из этапа C в модель:
  без них у адресной части нет источника истины (решение 5). Сама интеграция с ГАР —
  подсказки и импорт — остаётся в этапе C и зависит от ответа на вопрос 4.

**Термины.** «Объект» здесь всегда означает **объект обслуживания** (решение 6). Запись в
государственном реестре называется **адресным объектом реестра**, узел нашего дерева —
**узлом**.

Прототип, о котором идёт речь: [`prototypes/sip-setup/index.html`](../prototypes/sip-setup/index.html),
описание — [[07 - Прототип WEBUI - настройка SIP]].

## Итоговая схема

Модель делится на четыре слоя. Смысл деления: **от дома и ниже всё общее для любой
страны, выше дома всё национальное, а обслуживание вынесено из адреса.**

```
┌─ СТРАНОВОЙ ПРОФИЛЬ ─ данные, не код ───────────────────────────────────┐
│  уровни адреса и их допустимый порядок   (РФ: классификатор ГАР)       │
│  реестр адресов                          (РФ: ГАР / ФИАС)              │
│  шаблон печати адреса                                                  │
│  справочники типов помещений и типов панелей                           │
│  какой уровень считается входным        (РФ: 1, ЕС: 0)                 │
│  локаль: язык, формы слов, направление письма, имя уровня «подъезд»    │
└────────────────────────────────────────────────────────────────────────┘
            │ выбирается страной адресного корня, задаёт правила ниже
            ▼
┌─ АДРЕСНАЯ ЧАСТЬ ─ национальная, отражение реестра ─────────────────────┐
│  адресный корень (несёт страну) → элемент адреса → … → дом             │
│  у каждого узла: ссылка на реестр (РФ — ГУИД ГАР)                      │
│                   либо признак «нет в реестре»                         │
│  у дома: номер, корпус, строение, литера — раздельными полями          │
└────────────────────────────────────────────────────────────────────────┘
            │ дом — стык двух слоёв
            ▼
┌─ ЯДРО ДОМОФОНИИ ─ общее для всех стран ────────────────────────────────┐
│  дом → [подъезд] → этаж → помещение (тип) → SIP-аккаунт                │
│  панель: место установки = объект │ дом │ подъезд │ этаж │ помещение   │
│          + уровень (число) + тип панели + зона обслуживания            │
│  зона — правило; связки «панель ↔ помещение» — исключения из него,     │
│  задаются с любой стороны                                              │
└────────────────────────────────────────────────────────────────────────┘
            ▲
            │ ссылается на дома, сам в адресе не участвует
┌─ ОБСЛУЖИВАНИЕ ─ вне адресного дерева ──────────────────────────────────┐
│  объект обслуживания = один дом или группа домов                       │
│    (РФ — ЖК; за рубежом — estate, compound, condominium)               │
│  на нём: договор и лимиты, сервер Kamailio,                            │
│          граница зон и связок, пункт в селекторе объектов              │
│  страна не хранится, а выводится из домов:                             │
│          все дома объекта — в одной стране                             │
└────────────────────────────────────────────────────────────────────────┘
```

### То же за рубежом — меняется только верхний слой

```
Объект обслуживания: «Baker Street Estate» · сервер sip-uk-1 · страна GB

United Kingdom                адресный корень · страна GB → профиль GB
└ Greater London              элемент адреса · вид из профиля GB
  └ Camden                    элемент адреса
    └ Baker Street            элемент адреса · USRN 2405…
      └ 221B                  дом · UPRN 100081…
        └ Ground floor        этаж · уровень 0  ← входной уровень задан профилем
          └ Flat 3B           тип «flat» · номер «3B» (строка) · код вызова 303
```

Ядро домофонии, панели и зоны здесь ровно те же. Различия — только в профиле: другой
перечень видов адреса, другой реестр, входной уровень 0 вместо 1, буквенно-цифровой номер
помещения при числовом коде вызова.

### Что общее, что национальное

| | Общее ядро | Национальная часть |
|---|---|---|
| Дом, подъезд, этаж, помещение, аккаунт — сама модель | ✔ | |
| Панель: место установки, уровень, зона обслуживания | ✔ | |
| Зона как правило, связки «панель ↔ помещение» как исключения | ✔ | |
| Номер помещения (строка), код вызова (число), SIP-номер | ✔ | |
| Объект обслуживания, договор, лимиты, сервер | ✔ | |
| Уровни адреса и их порядок | | ✔ |
| Реестр адресов и ссылки на него | | ✔ |
| Формат печати адреса | | ✔ |
| Справочник типов помещений | | ✔ |
| Справочник типов панелей | | ✔ |
| Какой уровень входной (0 или 1) | | ✔ |
| Язык, формы слов, направление письма, имя уровня «подъезд» | | ✔ |

Два справочника — типов помещений и типов панелей — стоят в национальной части по одной
причине: «машиноместо» и «кладовая» так же неуниверсальны, как «калитка» и «дверь
подъезда». В ядре остаётся модель (у помещения есть поле «тип», у панели — поле «тип»),
в профиле — значения. Туда же уходит само слово «подъезд»: entrance, core, block,
staircase — это вопрос локали, а не структуры.

## Что не так сейчас

В прототипе цепочка жёсткая, у каждого уровня ровно один допустимый потомок
(словарь `CHILD_TYPE`):

```
регион → город → ЖК → дом → подъезд → этаж → квартира → аккаунт
```

Отсюда пять проблем. Первые две названы в [[08 - По настройке SIP]], остальные — следствия
той же жёсткости.

1. **Реальный адрес не всегда влезает.** «Москва — Зеленоград — корпус 1123 — кв. 8» — без
   улицы. Сейчас такой адрес не завести, а лишние уровни приходится выдумывать. Обратный
   случай — Москва с округами и районами, где уровней не хватает.
2. **Кроме квартир в доме есть другие помещения** — машиноместа, кладовые, офисы. Под
   каждое заводить свой уровень дерева нельзя, их слишком много.
3. **Панель некуда поставить по вертикали и некуда поставить на этаже.** Панель крепится
   только к территории ЖК, дому или подъезду (`MOUNT_TYPES`). Этаж местом установки не
   бывает вообще — поэтому калитка на подземном уровне в модели не выражается, а панель на
   **этажной (тамбурной) двери** или у двери лифтового холла не заводится в принципе.
4. **Без ЖК ничего не работает, а дома без ЖК существуют.** Частный дом, одиночная
   многоэтажка, здание с калиткой. В прототипе ЖК обязателен: окно создания панели
   отвечает «Сначала добавьте ЖК», лимиты и кандидаты в связках ищутся подъёмом по дереву
   до ЖК (`complexOf`).
5. **Российские допущения вшиты в код, а не в данные.** Страны нет вообще («Страна одна —
   РФ» написано прямо в подсказке окна создания), номер помещения разбирается как число,
   номер этажа вытаскивается выражением «Этаж N» и на «Этаж −1» не срабатывает, первым
   этажом считается 1, множественные формы — по правилам русского языка (`pluralRu`).
   Каждое из этих допущений при первой же зарубежной поставке становится переписыванием.

## Решения

### 1. «Помещение» с типом из справочника вместо «квартиры»

Уровень называется **помещение** — как и в списке уровней из [[08 - По настройке SIP]], —
и у него обязательное поле **тип** из справочника:

| Тип | Жилое | Пример |
|---|---|---|
| Квартира | да | кв. 45 |
| Апартаменты | да | апарт. 12 |
| Офис | нет | офис 3 |
| Машиноместо | нет | м/м 118 |
| Кладовая | нет | кладовая 7 |
| Техпомещение | нет | щитовая, насосная |

Базовый набор задаётся профилем страны. Установка может добавить свой тип — колясочная,
серверная, мастерская, офис УК — но не может удалить базовый: иначе импорт и отчёты
перестанут сходиться между установками. Полностью закрытый справочник не годится, список
реальных назначений длиннее любого заранее составленного.

**Почему так.** Это снимает давление на число уровней дерева: чтобы завести машиноместо,
не нужен новый уровень — нужно значение в справочнике. Один приём вместо пяти новых
сущностей. Тот же приём применён к адресной части (решение 5).

**Что тянет за собой:**

- **Номер помещения — строка, не число.** «Квартира 45», «3B», «12-C», «Unit 4/17».
  Сейчас номер вытаскивается регулярным выражением и участвует в подсказке SIP-номера —
  это допустимо как подсказка при создании, но SIP-номер не должен зависеть от номера
  помещения ничем другим.
- **Код вызова — отдельное числовое поле.** У панели цифровая клавиатура: гость набирает
  номер помещения. Пока номер был числом, отдельного поля не требовалось; со строковым
  номером набор на панели ломается. Поэтому у помещения три разных идентификатора, и
  путать их нельзя:

  | | Что это | Где уникален |
  |---|---|---|
  | Номер | то, что написано на двери; строка | внутри этажа |
  | Код вызова | то, что набирают на панели; целое число | внутри зоны каждой панели |
  | SIP-номер аккаунта | адрес в Kamailio | внутри realm |

  Код вызова по умолчанию берётся из цифр номера, если они там есть.
- **Признак «жилое» — поле типа, а не часть его названия.** SIP-аккаунты разрешены любому
  типу: у офиса домофон нужен. Но при массовом создании и импорте аккаунты по умолчанию
  заводятся только жилым, и решать это должен флаг, а не разбор строки «Офис (нежилое)».
- Автоподстановка имени идёт от типа («Квартира 46», «Машиноместо 119»), нумерация
  считается внутри своего типа: машиноместо 14 и квартира 14 в одном доме не конфликтуют.
- Уникальность email жильца считается внутри **помещения**, а не квартиры.
  Смысл правила не меняется.
- Счётчики и лимиты считают помещения, а не квартиры. Если лицензия считает SIP-аккаунты,
  считать надо аккаунты (⏸ вопрос 3).
- **Помещение на двух уровнях** — двухуровневая квартира, таунхаус — крепится к этажу
  входа, остальные занятые уровни идут справочным полем. Иначе инвариант «ровно один
  этаж» (решение 2) пришлось бы ломать ради редкого случая.

### 2. Этаж обязателен, но создаётся сам

**Правило:** на пути от дома до помещения всегда ровно один этаж. Пропусков нет.

**Почему так.** Необязательный уровень дороже обязательного. Как только этаж может
отсутствовать, каждый расчёт получает ветку «а если этажа нет»: этаж помещения, помещения
этажа, статистика по дому, подсказки при связывании. Один твёрдый инвариант дешевле
гибкости, которой почти никто не воспользуется. Этаж к тому же есть у любого помещения в
любой стране — выдумывать его не приходится, достаточно не спрашивать.

**Чтобы обязательность не превратилась в ручную работу:**

- этаж создаётся автоматически, когда помещение добавляют в дом напрямую (частный дом,
  одно помещение — «Этаж 1» появляется сам, с входным уровнем из профиля);
- если этаж в доме один, отдельной строкой в дереве он не показывается — уровень
  сворачивается, как предложено в §1.3 плана для цепочек с единственным потомком;
- свёртка отключается, как только у этажа появляется собственное содержимое — панель на
  этажной двери или свои настройки. Узел, на который надо нажать, должен быть виден.

**У этажа два поля: числовой уровень и название.** Уровень — целое число, название
необязательное («цоколь», «технический», «Ground floor»). Уникальна пара «уровень +
название»: это и даёт порядок сортировки (по уровню, затем по названию), и оставляет
место мезонину, антресоли и «этажу 5А» рядом с пятым. Границы ввода (−20…+200) нужны
только как защита от опечатки, смысла в них нет.

**Какой уровень входной — знает профиль страны, а не код.** В РФ это 1, в
континентальной Европе 0. Используется ровно в трёх местах: уровень автосозданного этажа,
уровень по умолчанию у панели на доме и подъезде, подпись «вход» в списках. Больше нигде
опираться на него нельзя: уровень — координата, а не смысл.

### 3. Подъезд остаётся — необязательным уровнем над этажом

Подъезд есть — этажи внутри подъездов. Подъезда нет — этажи прямо в доме.

**Почему его нельзя убрать.** В доме на четыре подъезда «Этаж 5» физически существует
четыре раза — это четыре разные лестничные клетки. Уберём подъезд, и квартиры 20, 21, 120
и 121 окажутся на одном этаже, а из какого они подъезда — уже не видно. Вместе с этим
теряется и зона «панель подъезда вызывает помещения своего подъезда».

**Почему он, в отличие от этажа, остаётся необязательным.** Подъезда может физически не
быть — частный дом, таунхаус, здание с одним входом, — а за пределами РФ понятие и
называется иначе, и встречается реже. Выдуманный «Подъезд 1» полез бы в печать адреса, в
имена панелей по умолчанию и в зоны обслуживания, то есть стал бы виден пользователю.
Цену необязательности при этом удаётся удержать в одной точке: ветка «а если подъезда
нет» живёт только в правиле «родитель этажа — подъезд, если он есть, иначе дом». Всё
остальное — статистика, зоны, кандидаты при связывании — считается от этажа и дома и о
подъезде не спрашивает.

### 4. Панель: любое место установки, плюс уровень и зона обслуживания

**Правило — одно, без исключений:** панель ставится на любой уровень-контейнер:

```
объект обслуживания │ дом │ подъезд │ этаж │ помещение
```

Помещение в этом списке не лишнее: индивидуальная панель у двери апартаментов, офиса или
коттеджа — та же панель с той же учёткой, только зона у неё из одного помещения.

У панели три поля вместо прежнего одного:

| Поле | Что это | Как заполняется |
|---|---|---|
| Уровень | этаж, на котором панель физически стоит: −1, 0, 1… | место «этаж» или «помещение» — берётся из этажа, менять нельзя; «дом» и «подъезд» — по умолчанию входной уровень профиля; «объект» — вручную (въезд 1, подземная калитка −1) |
| Тип панели | въезд, калитка, входная группа, дверь подъезда, этажная дверь, дверь помещения | из справочника профиля; по умолчанию — от места установки; от типа зависит имя по умолчанию |
| Зона обслуживания | какие помещения панель вызывает | правило; по умолчанию от места установки, можно изменить |

**Зона обслуживания по умолчанию:**

| Место установки | Зона по умолчанию | Пример |
|---|---|---|
| Объект | все помещения объекта | въезд на территорию, калитка |
| Дом | все помещения дома | входная группа |
| Подъезд | помещения подъезда | дверь подъезда |
| Этаж | помещения этажа | тамбурная дверь, дверь лифтового холла |
| Помещение | само помещение | панель у двери апартаментов |

**Почему появилось третье поле.** В прототипе сейчас от места установки зависит не только
адрес, но и то, кого панель вызывает: панель подъезда первой предлагает квартиры своего
подъезда. Пока мест установки было три и все они совпадали с зоной обслуживания, отдельное
поле было не нужно. Как только местом установки становится этаж, совпадение ломается:
калитка на подземном уровне стоит на −1, а вызывает весь объект. Значит зону обслуживания
надо сделать явной — тогда и «калитка на −1», и «тамбурная дверь на 5-м этаже» описываются
одним и тем же способом.

**Зона — правило, а не список.** Фактический перечень вызываемых помещений считается как
зона минус явно исключённые плюс явно добавленные. Из этого следует:

- новое помещение попадает в зону автоматически: интегратору не надо помнить о панели
  въезда, заводя 245-ю квартиру, и о ней не забудут при импорте;
- панель въезда на объекте из двадцати корпусов не порождает пять тысяч строк связок;
- слияние объектов (решение 6) расширяет зоны сразу, без переобхода панелей.

Связки «панель ↔ помещение» остаются сквозными и правятся с обеих сторон, но означают
теперь исключение из правила, а не сам факт вызова. В карточке видно и то и другое:
«вызывает: весь дом, кроме кв. 14; дополнительно — м/м 118».

**Код вызова уникален внутри зоны.** Это единственная проверка, которую нельзя отложить:
две квартиры с кодом 45 на одной панели означают, что одна из них с неё недостижима.
Конфликт возможен не только при вводе, но и при расширении зоны — при слиянии объектов
или смене места установки, — поэтому проверять его надо на обеих операциях, а не только
в карточке помещения.

### 5. Выше дома — один уровень «элемент адреса», виды из профиля страны

Вместо девяти разных уровней из таблицы в [[08 - По настройке SIP]] — **один тип узла
«элемент адреса»** с полем «вид», а перечень видов и допустимый порядок берутся из
профиля страны.

**Почему так.** Таблица менеджера верна как правило данных, но буквально в меню её
показывать нельзя: девять похожих формулировок при каждом создании замедляют работу, а
узлы создают сотнями. С одним типом узла меню остаётся одно — «Добавить элемент адреса» —
плюс выбор вида. Любой адрес заводится: и Зеленоград без улицы, и Москва с округом и
районом, и адрес в другой стране.

**Адресный корень несёт страну.** Дерево начинается с узла верхнего уровня — страны (в РФ
он один и создаётся сам). Профиль выбирается его страной, и всё, что ниже, — виды адреса,
реестр, входной уровень, справочники, локаль — берётся оттуда. Держать страну на объекте
обслуживания нельзя по двум причинам: объект появляется вместе с домом, то есть заведомо
позже, чем пользователь заводит «Москву» и выбирает вид этого узла; и адресные узлы
разделяются между объектами — на одной улице стоят дома разных ЖК, — так что профиль по
ним однозначно не выводится. Страна объекта — производная: она берётся от его домов, и
собрать в один объект дома из разных стран нельзя.

**Для РФ профиль — это ГАР.** Адрес в РФ нормирован федерально: 443-ФЗ от 28.12.2013 и
Правила присвоения адресов (ПП РФ № 1221 от 19.11.2014), оператор — ФНС, реестр — ГАР,
доступ через ФИАС. Отсюда:

- **перечень видов берём из классификатора уровней ГАР**, а не придумываем. Таблица из 08
  и справочник 89 субъектов из плана 09 становятся подмножеством реестра (вшитый список
  субъектов остаётся разумным offline-фолбэком);
- **дерево строим по муниципальной иерархии.** В ГАР иерархий две —
  административно-территориальная и муниципальная. Держать обе уровнями нельзя: у узла
  будет два родителя. Берём муниципальную как нормативную;
- **административные названия — метки, а не уровни.** Административных округов Москвы
  (ЦАО, ЗАО, ЗелАО) в муниципальном делении нет, а искать по ним будут. Метка висит на
  том узле, к которому относится, — ЗАО на муниципальном округе Раменки, — а не на каждом
  доме: иначе одно значение размножается по сотням строк и расходится при первой правке;
- **ссылку на реестр хранит каждый адресный узел, а не только дом.** Если ГУИД есть
  только у дома, переименование улицы подхватить нечем: наш узел «Мичуринский проспект»
  ни с чем не сопоставлен. Поэтому ГУИД адресного объекта лежит на каждом узле, а имена
  у нас — кэш для отображения. У дома, кроме ГУИДа, лежат структурные поля — номер,
  корпус, строение, литера: ГАР отдаёт их раздельно, и на них держатся сортировка,
  поиск и сопоставление, которые по слитной строке «дом 14, корп. 2» не работают;
- **режим «нет в реестре»** обязателен: новостройка попадает в ГАР с задержкой, а
  интегратор заводит объект раньше. Заводим вручную, помечаем, позже сопоставляем с
  ГУИД;
- **узлы не дублируются:** пара «вид + нормализованное имя» уникальна внутри родителя.
  Без этого правила один тип узла со свободным именем воспроизведёт ровно те дубли, ради
  которых он и вводился, — в демо-данных уже видно «Москва → Москва».

**У каждого вида есть признак «печатается в адресе / только навигация».** Район и
административный округ в адресную строку не входят («г. Москва, ул. Профсоюзная, д. 5»),
но в дереве нужны. Тот же признак закрывает подъезд, этаж и объект обслуживания — одно
поле вместо трёх частных исключений.

**Москва как субъект-город не дублируется.** Сейчас в демо-данных видно «Москва → Москва»
— план 09 отмечает это как путь к дублям. С одним типом узла Москва заводится один раз,
видом «субъект РФ (город федерального значения)», а ниже сразу муниципальный округ. То
же для Санкт-Петербурга и Севастополя.

**Глубина.** Над домом Москва по муниципальной иерархии даёт три адресных уровня;
административный округ в них не входит, он метка. Целиком цепочка — девять уровней:
страна → субъект → муниципальный округ → улица → дом → подъезд → этаж → помещение →
аккаунт. Это ровно тот случай, для которого §1.3 плана требует ограничить отступ,
склеивать цепочки с единственным потомком («Россия › Москва › Раменки») и показывать
полный путь в хлебных крошках. На Москве это требование перестаёт быть желательным.

Обязателен только корень со страной. Остальные адресные виды **необязательны** — правило
про порядок, а не про наличие.

### 6. ЖК: из иерархии убрать, как сущность сохранить

**ЖК сейчас играет две роли одновременно, и их надо развести:**

| Роль | Обязательна | Где живёт |
|---|---|---|
| Группа домов в адресе | нет — дом бывает сам по себе | нигде, из адреса убирается |
| Объект обслуживания: договор, лимиты, сервер, граница зон и связок, пункт селектора | **да, всегда** | отдельная сущность вне дерева |

Что делаем:

- **ЖК перестаёт быть уровнем адресного дерева.** Адресная часть чистая: элементы адреса
  → дом.
- **Появляется «объект обслуживания»** — сущность вне адреса. На него переезжает всё, что
  сейчас висит на ЖК: договор и лимиты, сервер Kamailio, граница зон обслуживания и
  связок «панель ↔ помещение», пункт в селекторе объектов.
- **Дом всегда принадлежит ровно одному объекту.** Создали дом — объект создался сам и
  равен этому дому. Несколько домов можно объединить в один объект, и тогда он получает
  имя ЖК. Для одиночного дома пользователь про объект не думает.
- **Слияние и разделение объектов — отдельная операция со своим сценарием.** Типовой путь
  интегратора — завести корпуса по одному и потом объединить, так что операция не
  экзотическая, а основная. При слиянии договор и лимиты берутся у одного из объектов
  явным выбором, остальные закрываются; сервер Kamailio должен совпадать, иначе слияние
  требует миграции и в один шаг не делается (по плану 09 — «объект = один сервер»); зоны
  панелей, заданные как «весь объект», расширяются на добавленные дома — это и есть смысл
  слияния, но показать последствия надо до подтверждения, вместе с проверкой кодов вызова
  на конфликт. При выносе дома обратно рвутся зоны и связки, уходящие за его границу, — их
  список показывается заранее.
- **Граница вызова, пока дома не объединены, — дом, а не ЖК.** Раньше панель одного дома
  могла звонить в квартиры соседнего просто потому, что ЖК был общим. Теперь для этого
  дома надо собрать в один объект. Это не потеря: объединение и означает «это одна
  территория».

**Почему так — четыре довода:**

1. **Дома без ЖК существуют.** Частный дом, одиночная многоэтажка, здание с калиткой.
   Пока ЖК обязателен, такой дом в системе не заводится.
2. **ЖК не влезает между улицей и домом.** Пока уровня «улица» нет, противоречие не
   видно. Решение 5 улицу вводит — и выясняется, что корпуса одного ЖК стоят на разных
   улицах («ул. Ленина 5 к. 1» и «ул. Мира 3» — один ЖК). Как узел адреса ЖК заставит
   соврать в адресе, и внутри дерева это не поправить.
3. **ЖК уже уходит из дерева по самому плану 09.** В §1.1 п. 2 решено перенести
   переключатель ЖК в левое меню как «Объекты на обслуживании». Держать одну сущность и в
   селекторе, и уровнем дерева — дублирование.
4. **«ЖК» — понятие российское.** За рубежом это estate, gated community, compound,
   condominium. Нейтральный «объект обслуживания» переводится словарём, уровень дерева с
   названием «ЖК» — нет.

Всё, что план 09 защищал своим ❌, сохраняется: ЖК остаётся объектом обслуживания, на нём
по-прежнему висят панели въезда, он по-прежнему единица в селекторе. Он лишь перестаёт
быть родителем в адресе.

**Побочная выгода.** Закрывается вопрос 1 плана 09 — «ключ распределения по серверам
Kamailio: ЖК или дом?». Ответ: объект обслуживания, который для одиночного дома и есть
дом.

### 7. Экспорт: страновой профиль и четыре инварианта

Локализацию, RTL и профили других стран сейчас делать рано. Но четыре инварианта надо
заложить сразу — потом они стоят переписывания, а сейчас это несколько полей:

1. **Страна — на адресном корне, профиль выбирается по ней.** Сейчас страны в модели нет
   вообще. У объекта обслуживания страна производная — от его домов.
2. **Адрес — через провайдера, со ссылкой на внешний реестр и режимом «нет в реестре».**
   Реестры разные: в Нидерландах, Дании и Франции они полноценные, в Британии есть ключи
   на объект (UPRN) и на улицу (USRN), но полной иерархии над ними нет, в Германии и США
   единого национального реестра нет вовсе. ГАР — пример профиля, а не часть модели.
   Режим «нет в реестре», который нужен для новостроек, для страны без реестра становится
   постоянным — то есть за это мы уже заплатили.
3. **Этаж — число плюс название**, входной уровень задаётся профилем (РФ 1, ЕС 0).
4. **Номер помещения — строка, код вызова — число**, SIP-номер не зависит ни от того, ни
   от другого.

Что можно отложить, но нельзя забыть: формат печати адреса шаблоном профиля (порядок
элементов разный: «ул. Ленина, 5» против «5 Main Street»); язык и формы слов через
словарь локали (в русском три формы, в английском две, в арабском шесть — сейчас в
прототипе `pluralRu`); поддержка письма справа налево для арабских рынков; справочники
типов помещений и типов панелей как часть профиля.

Прецедент в репозитории уже есть: [`prototypes/operator/i18n-en.js`](../prototypes/operator/i18n-en.js)
— словарь по русским строкам, где машиноместо переведено как «sp.», а уровень показан
как «−1».

## Что это меняет в прототипе

Перечень для оценки объёма, не инструкция:

- словарь допустимых потомков и список типов узлов: вместо восьми жёстких уровней —
  адресный корень со страной, «элемент адреса» с видом, дом, подъезд, этаж, помещение,
  аккаунт;
- граница арендатора: вместо «выбранный ЖК» — «выбранный объект обслуживания»; подъём по
  дереву до ЖК (`complexOf`) заменяется ссылкой дома на объект;
- договор, лимиты и подписка переезжают с узла ЖК на объект (подписка по плану 09 всё
  равно скрывается флагом — удачный момент для переноса); слияние и разделение объектов
  как отдельная операция с предпросмотром;
- карточка панели: три новых поля (уровень, тип, зона обслуживания), этаж и помещение как
  допустимые места установки, панели объекта показываются в его карточке и в линзе
  «Оборудование»;
- связки: из «списка вызываемых квартир» становятся исключениями из зоны; окна привязки
  показывают зону и дельту к ней, а не плоский список кандидатов;
- карточка помещения: поле «тип» с признаком «жилое», номер строкой, код вызова отдельным
  числовым полем, подписи и множественные формы («Квартир» → «Помещений»);
- карточка дома: номер, корпус, строение и литера раздельными полями вместо одной строки
  названия;
- автоподстановка имён: имя от типа помещения и от типа панели, номер этажа отдельным
  числовым полем, поддержка отрицательных уровней в нумерации и сортировке (`nextNumber`
  сейчас разбирает только «Этаж N» с положительным N);
- статистика в карточках дома, подъезда и этажа;
- подсказки при связывании — считаются от зоны обслуживания, а не от родителя панели;
- страна на адресном корне и заготовка профиля: справочники и правила читаются из данных,
  а не из констант в коде (`CHILD_TYPE`, `MOUNT_TYPES`, `pluralRu`);
- демо-данные: дом без ЖК, объект из двух корпусов, помещения нежилых типов, панель на
  этажной двери, панель на подземном уровне;
- поведенческие проверки [`tests/run.js`](../prototypes/sip-setup/tests/run.js) и список
  [`tests/checklist.md`](../prototypes/sip-setup/tests/checklist.md): ожидания по числу
  квартир, проверки «только своего ЖК», текст ошибки про уникальность email внутри
  квартиры.

## Этапность

**Сейчас, для РФ.** Помещение с типом, строковым номером и кодом вызова; обязательный
этаж с числовым уровнем; необязательный подъезд; панель с уровнем, типом и зоной
обслуживания; зона как правило и связки как исключения; объект обслуживания вместо ЖК как
уровня; «элемент адреса» с видом и перечнем видов из классификатора ГАР; структурные поля
дома.

**Сразу, но дёшево — только как поля и структура.** Адресный корень со страной; ссылка
каждого адресного узла на внешний реестр и режим «нет в реестре»; справочники (виды
адреса, типы помещений, типы панелей, входной уровень) читаются из профиля, а не вшиты.

**Потом.** Подсказки и импорт из ГАР (зависит от ответа на вопрос 4); профили других
стран; шаблоны печати адреса; локализация, формы слов, письмо справа налево.

## Открытые вопросы

1. **Нужен ли уровень над объектом обслуживания?** Управляющая компания обслуживает
   несколько ЖК; если объект — единица договора и сервера, то у УК объектов несколько.
   План 09 в §1.1 п. 2 уже предполагает группировку «УК → ЖК» в селекторе, то есть
   вводит УК неявно. От ответа зависит, становится ли она сущностью с собственными
   настройками и правами, и может ли один объект включать дома в разных городах.
2. **Что ещё, кроме панели, может стоять на этаже?** Этажный блок вызова, лифтовой
   контроллер, группа доступа по этажам. Если да — у этажа появятся свои настройки, и
   уровень станет полноценной точкой монтажа оборудования, а не только координатой.
3. **Лицензия считает помещения или SIP-аккаунты?** От этого зависит, что показывать в
   счётчиках вместо лимитов тарифа (⏸ вопрос 4 плана 09).
4. **Как получаем ГАР** — периодический импорт выгрузки или сервис подсказок, и доступен
   ли он в закрытом контуре (⏸ вопрос 5 плана 09). Без ответа адресная часть остаётся на
   ручном вводе, а ссылки на реестр заполняются вручную.
5. **Нужны ли SIP-аккаунты машиноместам и кладовым по умолчанию.** Модель их разрешает;
   вопрос в дефолтах массового создания, импорта и демо-данных: заводить ли аккаунт
   нежилому помещению, или оно только объект привязки к панели въезда.
6. **Первая зарубежная страна** — какая? От неё зависит, какой профиль делать вторым и
   нужен ли сразу RTL и требования к месту хранения персональных данных.
