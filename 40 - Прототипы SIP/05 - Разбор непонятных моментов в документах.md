## 1. Зачем на первом этапе WebRTC?

**Цитата (ТЗ):** WebRTC — «для приёма аудио/видео с домофонных панелей при входящих вызовах»; SIP-коннектор «при вызове подключает камеру панели к веб-клиенту через WebRTC».

**Почему это плохо как блокер этапа 1:**

- Панели говорят на **SIP + RTP** (H.264 / G.711…), не на WebRTC.
- Мобильные прототипы **уже** принимают вызов по SIP/RTP (Linphone), с видео и звуком, с push из фона — на sip-test1.
- WebRTC нужен **только браузеру**, которому нельзя дать «сырой» SIP/RTP без шлюза (ICE + DTLS-SRTP ± транскод). Это отдельный дорогой медиа-слой.

**Как правильно:**

| Участник | Этап 1 (пилот) | Позже (опционально) |
|---|---|---|
| Жилец / оператор на телефоне-планшете | Нативный SIP (как сейчас) | — |
| Диспетчерская в браузере | Факт звонка в UI + при необходимости запись/расшифровка; **живой ответ с SIP-устройства** | Полноценный WebRTC-ответ через шлюз |
| Постоянное видео панели | **RTSP → Next / Intellect X** (не WebRTC и не SIP) | — |

Вывод: WebRTC **не** обязателен для первого этапа домофонии. Тянуть SIP↔WebRTC-шлюз (Janus/FreeSWITCH/RTPEngine в WebRTC-профиле + TURN) в пилот — раздувание scope. В концепции v2 (§2.5) разделение «браузер = WebRTC, мобильный = SIP» уже сформулировано верно; ошибка — ставить веб-ответ в критический путь этапа 1.

## 2. Почему у оператора не может быть SIP-телефона / планшета?

**Может и должен.**

Тот же Kamailio + sipmanager + аккаунт «оператор/консьерж» + приложение (или готовый Linphone) закрывают ответ на вызов **без** браузерного WebRTC. Прототипы iOS/Android это уже показали на реальной панели Beward и на softphone-имитации.

Альтернатива, предложенная при разборе документов и согласованная с жизнью:

1. В вебе — **факт звонка** (событие от sipmanager / Kamailio webhook), статус, кто звонит, куда.
2. При необходимости — запись разговора / расшифровка из медиапайплайна (отдельная задача хранения).
3. **Ответ** — с оперативного телефона/планшета по SIP.

«Оператор обязан сидеть в браузере и принимать медиа только через WebRTC» — искусственное ограничение, не требование панелей и не следствие уже построенного облака.

## 3. «SIP-коннектор (мост)» — смешение ролей и лишняя сущность

**Цитата (ТЗ):**

> SIP-коннектор (мост) (по идее это наш ITV-Cloud)  
> — Связывает SIP-сервер с ядром Интеллект X и веб-интерфейсом.  
> — Транслирует SIP-события … в REST API.  
> — Принимает команды («открыть дверь») и преобразует их в SIP-команды или HTTP-запросы к панели.  
> — Управляет видеопотоком: при вызове подключает камеру панели к веб-клиенту через WebRTC.

**Что не так:**

1. **Уже есть sipmanager** ([axxoncloudgo](ssh://git@src.axxonsoft.dev/proj/axxoncloudgo.git)) — дерево панелей/аккаунтов, share, push, webhook `/calls`, запись в Kamailio. Это и есть «связь SIP-сервера с облачным UI/API», без фантазийного названия.
2. **Открытие двери через «SIP-команды» как основной путь** — см. §4: для многих панелей это не нужно и не принято как единственный способ.
3. **WebRTC при вызове** — смешивает звонок, VMS-видео и браузерный плеер в один клубок. Камера панели должна жить в VMS по RTSP (§5); звонок — отдельно по SIP.

В концепции v2 коннектор уже назван «собственный микросервис», а не «ITV-Cloud» — лучше, но обязанности всё ещё раздуты (дверь + WebRTC + события). Разделить:

| Сервис | Ответственность |
|---|---|
| sipmanager + Kamailio | SIP identity, маршрутизация, push, событие «звонок» |
| VMS / Next | RTSP камеры панели, архив, аналитика |
| Device / ACS integration | HTTP/MQTT/SDK «открыть дверь» |
| (позже) WebRTC gateway | Только если нужен ответ из браузера |

## 4. Отсутствующее API: открыть домофон без SIP-звонка

**Проблема в документах:** акцент на «проброс» открытия через SIP (DTMF / SIP INFO / «события через SIP»). Так делают *во время* разговора как запасной канал; **многие панели открываются без любого SIP**.

**Правильный паттерн:**

```text
Клиент / Next / бэкенд
    │  REST «unlock door»
    ▼
Интеграция (драйвер модели панели)
    │  HTTP / MQTT / vendor SDK
    ▼
Панель → реле замка
```

SIP в этой цепочке **не участвует**.

### Beward (подтверждено практикой и документацией)

- Линейки вызывных панелей **DKS / DS** и др.: веб-интерфейс, **RTSP** поток камеры (`rtsp://…/av0_0` и варианты — см. manuals / iSpy), HTTP-порт для управления.
- Во время SIP-звонка дверь часто открывают **DTMF** (настраиваемые коды «Open main door» / alt door) — это то, что делают текущие мобильные прототипы (`#`).
- Вне звонка: управление через HTTP/CGI/REST панели (вендорский web API; community: [py-beward](https://github.com/Limych/py-beward), примеры REST к DKS-15374). Конкретный URL unlock зависит от модели/прошивки — нужен драйвер **по модели**, не «общий SIP INFO».
- Бытовой факт: приложение **«МТС домофон»** + панель Beward — открытие и просмотр видео **без** входящего звонка. Значит, у панели (или у облака оператора поверх её API) есть путь мимо SIP.

### Типично у других вендоров (тот же принцип)

| Вендор | Открытие вне SIP | Видео вне SIP |
|---|---|---|
| **Beward** | HTTP/CGI/REST к панели | RTSP / HTTP snapshot |
| **BAS-IP** | HTTP API панели / Link | RTSP |
| **Akuvox** | HTTP API / Cloud API | RTSP |
| **Fanvil / 2N** | HTTP / REST | RTSP / ONVIF часто |

Итог для Next / Intellect X: завести **модель устройства «вызывная панель»** с capability `unlock` (HTTP/MQTT) и capability `camera` (RTSP URL), а не эмулировать кнопку двери SIP-событиями в ядре.

DTMF/`#` в мобильном приложении оставить как **удобство во время разговора**, не как единственное API продукта.

## 5. RTSP панели в Next — без SIP и без звонка

**Требование:** постоянно видеть картинку с камеры домофона и делать всё, что умеет Next / Intellect X (live, архив, аналитика, раскладки), **не запуская SIP**.

**Как устроено у Beward и аналогов:** камера панели — обычный IP video source с RTSP (часто порт 554, путь вроде `/av0_0`). Её добавляют в VMS **как камеру**, независимо от SIP-аккаунта панели.

```text
Панель ──RTSP──► Next / Intellect X   (всегда: live / archive / analytics)
Панель ──SIP───► Kamailio ──► мобильный / операторский SIP UA  (только звонок)
Бэкенд ──HTTP──► Панель unlock         (дверь без звонка)
```

Смешивать «при вызове подключить камеру к WebRTC» — антипаттерн: VMS уже умеет RTSP; WebRTC-шлюз не нужен, чтобы «просто видеть двор».

## 6. Плагин + BareSIP + «виртуальные устройства» — оторвано от жизни

**Цитата (ТЗ):**

> Плагин создаёт виртуальные устройства «SIP-панель» и «SIP-аккаунт жильца».  
> При добавлении панели плагин автоматически генерирует SIP-конфигурацию для **BareSIP**…  
> При вызове плагин транслирует SIP-события в WebSocket…

**Почему это безграмотно / устарело:**

1. **BareSIP** — это SIP *user agent* (библиотека/клиент), а не SIP-*сервер*. Писать «SIP-сервер на базе BareSIP» — путаница классов ПО. Сервер в облаке — **Kamailio** ([kamailio](ssh://git@src.axxonsoft.dev/new/kamailio.git)); клиент — Linphone / панель.
2. Провижининг аккаунтов уже делает **sipmanager** → Kamailio HTTP API, админка — раздел SIP в [axxoncloud-ui](ssh://git@src.axxonsoft.dev/proj/axxoncloud-ui.git). Отдельный «плагин, генерирующий конфиг BareSIP» не нужен.
3. «Виртуальные устройства SIP-панель / SIP-аккаунт» внутри плагина Интеллект X дублируют облачное дерево без выигрыша для маршрутизации звонков. Имеет смысл **привязка** панели к объекту в VMS (камера RTSP + unlock), а не эмуляция SIP UA плагином.
4. Трансляция событий звонка: уже есть webhook Kamailio → sipmanager `/calls` (+ push). WebSocket в UI — нормальный UX поверх этого API, не поверх «плагина BareSIP».

## 7. Рекомендуемая целевая модель этапа 1

Опираться на то, что **уже работает**, и добавить недостающие куски без WebRTC:

```text
[Уже есть]
  Kamailio + RTPEngine
  sipmanager (axxoncloudgo feature/sipmanager_microservice)
  AxxonNet UI: раздел SIP
  iOS / Android SIP-клиенты (Linphone), push, ответ A/V, DTMF в звонке

[Добавить на этапе 1]
  HTTP (или MQTT) unlock по моделям панелей (Beward в приоритете)
  RTSP камеры панели как обычная камера в Next / Intellect X
  Операторский SIP-аккаунт на телефон/планшет (не браузерный WebRTC)

[Отложить]
  SIP↔WebRTC шлюз и ответ из браузера
  «Универсальный SIP-коннектор» как отдельная сущность
  Плагинная генерация BareSIP-конфигов
```

Критерий готовности пилота домофонии: жилец и оператор принимают вызов с панели; дверь открывается **и** из звонка (DTMF), **и** без звонка (HTTP); картинка панели всегда в Next по RTSP. Всё это совместимо с текущим sip-test1-контуром и не требует WebRTC на старте.
