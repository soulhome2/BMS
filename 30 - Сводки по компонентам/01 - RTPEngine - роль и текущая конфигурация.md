# RTPEngine — роль и текущая конфигурация

> **Статус:** Сводка к фиксации · **Дата:** 2026-08-04
>
> Разбор фактической роли и конфигурации RTPEngine в ядре домофонии. Опирается на [[02 - Концепция интегрированной цифровой экосистемы управления МКД (v2)]] §2.2, §7.1, §7.4, [[03 - Состояние Kamailio]] и [[06 - Устройство SIPManager]].

---

## Краткий ответ

Сейчас RTPEngine — это **медиарелей (RTP relay) для классических SIP/RTP-звонков**: пропускает через себя медиа (видео + звук) между панелью и мобильным SIP UA и мостит NAT. Это **не** WebRTC-шлюз и **не** транскодер — в текущем конфиге он делает ровно одну вещь: relay RTP/NAT.

---

## Точная конфигурация (по факту репозитория деплоя)

| Параметр | Значение |
|---|---|
| Что это | Отдельный процесс/контейнер (`rtpengine` в compose), медиарелей |
| Управление | Kamailio по UDP control socket `:2223` (NG-протокол) |
| RTP-порты | `10000–10100/udp` (100 портов), прокидывает наружу |
| Профиль | `rtpengine_manage("… ICE=remove RTP/AVP")` — **классический SIP/RTP**, ICE снимается |
| Шифрование | Нет — медиа идёт по **RTP/AVP** без SRTP |

> Цитата [[03 - Состояние Kamailio]]: «Медиа: `rtpengine_manage("… ICE=remove RTP/AVP")` — **классический SIP/RTP**, ICE снимается. Это **не** DTLS-SRTP / WebRTC для браузера.»

---

## Что он делает в звонке

```text
Панель (SIP UA) ──RTP──► RTPEngine ◄──RTP── Мобильный SIP UA (Linphone)
                            │
                   мостит NAT, релеит медиа
```

1. **Релей медиа каждого вызова** — видео (H.264) и аудио (G.711/G.722/Opus) между панелью и мобильным проходят через RTPEngine, а не напрямую.
2. **NAT-обход** — панель стоит в локальной сети дома, мобильный может быть в интернете за своим NAT. RTPEngine мостит RTP между ними (без него прямой RTP между разными NAT не дойдёт).
3. Это и есть то, что позволяет мобильному **«из любой точки»** принимать видеовызов — релей мостит трафик.

На стенде `sip-test1` проверено: «медиа (видео + звук) через RTPEngine-путь» ([[03 - Состояние Kamailio]]).

## Чего RTPEngine СЕЙЧАС НЕ делает

В текущей конфигурации он узконаправлен:

| Чего нет | Почему |
|---|---|
| **WebRTC-шлюз** | Профиль `ICE=remove` снимает ICE; нет DTLS-SRTP. Браузеру нужен другой профиль (ICE/DTLS) или отдельный медиасервер — не сделано и не нужно для мобильного пилота ([[05 - Разбор непонятных моментов в документах]]). |
| **Транскод кодеков** | Панели и мобильные говорят на общих кодеках (H.264/G.711), транскод не нужен. Транскод/early-media/конференции — роль B2BUA (Asterisk/FreeSWITCH), не relay ([[02 - SIP-сервер - Kamailio vs Asterisk]]). |
| **SRTP (шифрование медиа)** | Медиа идёт по RTP/AVP без шифрования. TLS/SRTP — **целевое состояние**, не текущее (концепция §2.2, §7.4). |
| **Терминирование медиа как B2BUA** | Он релей (proxy-подобная роль), не стоит «в разрыве» как PBX. |

> Цитата [[03 - Состояние Kamailio]]: «RTPEngine здесь — relay для SIP/RTP, а не обязательный WebRTC-gateway. Для браузерного ответа нужен был бы другой профиль (ICE/DTLS) или отдельный медиасервер — это не сделано и не нужно для мобильного пилота.»

---

## Ключевое ограничение — диапазон портов

Из концепции §7.1:

> «Ограничение текущей конфигурации: RTPEngine отдаёт RTP-диапазон `10000–10100`, то есть 100 портов. При аудио + видео это порядка 12–25 одновременных вызовов, а не 50. Диапазон необходимо расширить и зафиксировать расчёт «портов на вызов» (с учётом RTCP-mux) в Приложении D.»

То есть **сейчас система упирается в ~12–25 видеовызовов**, а целевая ёмкость — ≥ 50. Расширение RTP-диапазона — работа Этапа 1 пилота.

---

## Архитектурное место

- **Часть ядра** (концепция §2.2): «Сигнализация и медиа-релей — часть ядра, а не отдельный слой над видеоплатформой. WebRTC-компоненты вынесены в опцию».
- Паттерн **Kamailio (сигнализация) + RTPEngine (медиа)** — классический масштабируемый ([[02 - SIP-сервер - Kamailio vs Asterisk]]).
- На тираже (Этап 3) — несколько узлов Kamailio/RTPEngine для горизонтального масштабирования и HA; сейчас контур **один, без HA** ([[05 - Готовность решения - 2026-07-30]]).

---

## Целевое / будущее (не текущее)

| Что | Когда |
|---|---|
| TLS для сигнализации + SRTP для медиа | Целевое состояние, включение по объектам на Этапе 0 |
| WebRTC-шлюз (ICE/DTLS профиль или Janus/FreeSWITCH) | Опция, только для ответа из браузера — вне этапа 1 |
| Несколько узлов RTPEngine + HA | Этап 3/5 (тираж) |
| Расширение RTP-диапазона до ≥ 50 вызовов | Этап 1 (пилот) |

---

## Краткое определение

**Сейчас RTPEngine = медиарелей RTP для SIP-звонков: мостит NAT и пропускает через себя видео+аудио между панелью и мобильным.** Профиль классический (`ICE=remove RTP/AVP`), без WebRTC, без транскода, без SRTP. Узкое место сегодня — диапазон `10000–10100` (≈12–25 видеовызовов вместо ≥ 50). WebRTC-шлюзом он не является и для пилота не должен быть — браузерный ответ вынесен в опцию.
