# Открытие двери — DTMF и HTTP-unlock

> **Статус:** Сводка к фиксации · **Дата:** 2026-08-04
>
> Разбор двух независимых путей открытия двери домофона: DTMF в звонке и HTTP-unlock вне звонка. Опирается на [[02 - Концепция интегрированной цифровой экосистемы управления МКД (v2)]] §3.1.6, §8, §9 и [[05 - Разбор непонятных моментов в документах]] §4, §5.

---

## Два пути открытия двери

Концепция (§3.1.6) фиксирует **два независимых пути** и явно расставляет приоритеты:

> «6. **Открытие двери.** Два независимых пути: **вне звонка** — REST «unlock» → драйвер модели панели → HTTP/CGI/MQTT (**основной путь продукта**); **в звонке** — DTMF из приложения (удобство). SIP в первом пути не участвует.»

| | DTMF (в звонке) | HTTP-unlock (вне звонка) |
|---|---|---|
| Когда | Во время активного SIP-разговора | В любой момент, без звонка |
| Как | Тональный код (например `#`) внутри RTP-сессии | HTTP/CGI/REST-запрос к панели |
| SIP участвует? | Да (внутри звонка) | **Нет** |
| Роль в продукте | Удобство | **Основной путь продукта** |
| Сегодня | ✅ Работает в прототипах (`#`) | ❌ Отсутствует полностью |

---

## Что такое HTTP-unlock

**HTTP-unlock** — открытие замка домофона HTTP/CGI/REST-запросом напрямую к вызывной панели, **без поднятия SIP-звонка**. SIP в этом пути не участвует вообще.

Путь (док. 05 §4):

```text
Клиент / Next / бэкенд
    │  REST «unlock door»
    ▼
Интеграция (драйвер модели панели)
    │  HTTP / MQTT / vendor SDK
    ▼
Панель → реле замка
```

Параллельные независимые каналы панели:

```text
Панель ──RTSP──► VMS / Next              (всегда: live / архив / аналитика)
Панель ──SIP───► Kamailio ──► мобильный   (только звонок)
Бэкенд ──HTTP──► Панель unlock            (дверь без звонка)
```

---

## Модель устройства «панель» (capability)

Концепция определяет модель устройства «вызывная панель» с двумя capability:

> «Драйвер вызывной панели — модель устройства с capability **`unlock`** (HTTP/CGI/vendor API, по модели панели) и **`camera`** (RTSP URL). Открытие двери не требует ни SIP-звонка, ни видеоплатформы; DTMF в звонке остаётся удобством, а не единственным API.»

| Capability | Реализация | Зависимость |
|---|---|---|
| `camera` | RTSP URL (`rtsp://…/av0_0`) | Вне SIP, вне звонка |
| `unlock` | HTTP/CGI/vendor API | Вне SIP, вне звонка; **по модели панели** |
| (отдельно) | SIP UA → Kamailio | Только сам звонок |

---

## Почему HTTP-unlock — основной путь, а не DTMF

Аргумент (док. 05 §4): **многие панели открываются без какого-либо SIP**. Исходное ТЗ ошибочно ставило акцент на «проброс» открытия через SIP (DTMF / SIP INFO / «события через SIP») — но это запасной канал *во время* разговора.

**Beward** (подтверждено практикой и документацией):
- Линейки DKS / DS: веб-интерфейс, RTSP-поток, HTTP-порт управления.
- Вне звонка — HTTP/CGI/REST панели (вендорский web API; community [py-beward](https://github.com/Limych/py-beward), примеры REST к DKS-15374).
- **Конкретный URL unlock зависит от модели и прошивки** — нужен драйвер по модели, не «общий SIP INFO».
- Бытовой факт: приложение «МТС домофон» + Beward — открытие и видео **без** звонка.

**Тот же принцип у других вендоров:**

| Вендор | Открытие вне SIP | Видео вне SIP |
|---|---|---|
| Beward | HTTP/CGI/REST к панели | RTSP / snapshot |
| BAS-IP | HTTP API панели / Link | RTSP |
| Akuvox | HTTP API / Cloud API | RTSP |
| Fanvil / 2N | HTTP / REST | RTSP / ONVIF |

> Вывод (док. 05): «DTMF/`#` в мобильном приложении оставить как **удобство во время разговора**, не как единственное API продукта.»

## Кто вызывает HTTP-unlock (концепция §8, роли)

REST «unlock» может инициировать:

| Роль | Что может с дверью |
|---|---|
| Жилец | Открытие своей двери/шлагбаума (кнопка в приложении, без звонка) |
| Консьерж / оператор | Открытие двери с планшета |
| Диспетчер УК | Управление доступом (дверь, шлагбаум), подтверждение тревог |

Сценарий: жилец в приложении нажимает «открыть дверь» → запрос в облако → драйвер модели панели → HTTP на панель → реле замка. **Без поднятия трубки, без SIP-сессии.**

---

## Обязательство по аудиту (§15)

Открытие двери — **событие безопасности**. Путь HTTP-unlock несёт обязательства (док. [[01 - Выбор базовой архитектуры - платформа или надстройка над VMS]] §15):

> «Единый журнал. Результат команды и события устройства обязаны вернуться в облако и попасть в общий журнал (кто, что, когда, каким способом). Открытие двери — событие безопасности, и разрыв аудита недопустим.»

> «Явный результат, correlation ID, таймаут. Проксирование идемпотентно и различает три исхода: **выполнено, отказ, недоступно**.»

Антипаттерн (§2.3 концепции): заготовка `POST /api/call/initiate`, которая логирует запрос и возвращает success, ничего не отправив, — повторять нельзя. HTTP-unlock должен быть **идемпотентным** и возвращать реальный результат.

## HTTP-unlock при обрыве WAN — тонкость

Связано с [[02 - Локальный резерв SIP - обрыв WAN]]. **Два разных случая** ведут себя по-разному:

| Случай | Без WAN? |
|---|---|
| **Локальный HTTP-unlock** (§7.2) — локальный узел шлёт HTTP-команду панели в той же LAN | ✅ Сохраняется — облако не нужно |
| **HTTP-unlock из облака** (§15, путь «облако → драйвер → устройство») | ❌ Не работает — даже когда панель и устройство в двух метрах |

> §15: «Если конкретную калитку нужно открывать и без WAN, её либо нельзя вешать на этот путь, либо **локальный резервный узел должен уметь отдать команду напрямую** — это отдельное проектное решение, а не следствие.»

## Фактическое состояние (на 2026-07-30)

| Что | Статус |
|---|---|
| HTTP-unlock (REST unlock вне звонка) | **Отсутствует полностью** |
| Открытие двери — есть только | **DTMF в звонке** (прототипы `#`) |
| Кнопка «открыть дверь» в cloud UI | Нет |
| Драйверы панелей (`unlock` по моделям) | Не написаны |

> Критерий готовности пилота (док. 05): «дверь открывается **и** из звонка (DTMF), **и** без звонка (HTTP)».

> План (концепция, Этап 1): «HTTP-unlock **по моделям панелей**» (Beward в приоритете).

---

## Почему это важно для продукта

- **Базовая** функция — входит в конфигурацию **без лицензий VMS** (концепция §9: «открытие двери (в звонке DTMF и вне звонка HTTP)» в базовой поставке).
- Драйвер `unlock` пишется **под модель и прошивку** — «общего SIP INFO не существует» ([[04 - Оценка трудозатрат - МКД]], риск №3). Чем шире матрица панелей, тем дороже.
- Часть модели устройства «панель» (`unlock` + `camera`), проектируемой на Этапе 0.

---

## Краткое определение

**HTTP-unlock** = открытие замка домофона HTTP/CGI/REST-запросом к панели, **без SIP-звонка**. Путь: приложение/UI → REST «unlock» → драйвер модели панели → HTTP/MQTT/vendor API → панель → реле. SIP не участвует. **Основной путь продукта** (в отличие от DTMF в звонке — «удобство»). Сегодня не реализован (есть только DTMF); входит в пилот (Этап 1) как драйверы под конкретные модели панелей.
