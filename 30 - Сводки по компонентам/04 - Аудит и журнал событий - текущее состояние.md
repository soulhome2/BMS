# Аудит и журнал событий — текущее состояние

> **Статус:** Сводка к фиксации · **Дата:** 2026-08-04
>
> Разбор фактического состояния аудита и журнала событий в ядре домофонии. Опирается на [[02 - Концепция интегрированной цифровой экосистемы управления МКД (v2)]] §2.3, §6.3, §15, [[05 - Готовность решения - 2026-07-30]] §3.2–3.3, §4 и [[06 - Устройство SIPManager]].

---

## Краткий ответ

В текущей реализации **аудита в смысле концепции (§15 — единый журнал безопасности) нет**. Есть только «сырой» SIP-accounting на уровне Kamailio и webhook для push — но это не аудит.

---

## Что ЕСТЬ (минимум — это не аудит)

| Что | Где | Что это на самом деле |
|---|---|---|
| **Kamailio `acc`** (accounting) | таблица `acc` в Postgres Kamailio | Логирование SIP-диалогов (INVITE/BYE с `Call-ID`) — CDR-уровень. Это **SIP-события**, не бизнес-события безопасности. |
| **Webhook `/calls`** | Kamailio → `POST /api/v1/sipmanager/calls` | На начальном INVITE асинхронно шлёт `{sipNumber, callerNumber, callId}` в sipmanager. Это **триггер push**, не журнал. |
| **API истории звонков (возможно)** | на стороне `sipmanager`/Kamailio | «API на стороне ядра для этого уже есть» (концепция §6.3), но **экрана нет**. |

То, что есть — это «трансляция SIP-событий» (концепция §2.3): Kamailio → sipmanager → push. Это доставка вызова, а не аудит.

---

## Чего НЕТ

**1. Единого журнала нет.** Обязательство из §15 ([[01 - Выбор базовой архитектуры - платформа или надстройка над VMS]]):
> «Единый журнал. Результат команды и события устройства обязаны вернуться в облако и попасть в общий журнал (кто, что, когда, каким способом). Открытие двери — событие безопасности, и разрыв аудита недопустим.»

**2. Событийного канала для UI (WebSocket/SSE) нет вовсе** ([[05 - Готовность решения - 2026-07-30]] §3.3):
> «Событийного канала для UI нет вовсе — дашборд, журнал и «активные вызовы» опираются на несуществующую часть.»

И концепция §2.3:
> «Событийная модель для UI — к разработке. WebSocket/SSE в ядре отсутствует: в `sipmanager` нет ни endpoint'ов, ни обработки `Upgrade`, ни описания в OpenAPI; подтверждённый канал UI ↔ ядро — только REST.»

**3. «Аудит доступа и журнал событий» — в списке незрелого** ([[05 - Готовность решения - 2026-07-30]] §4):
> «…не сделано именно то, что проявляется только на реальном доме и только через несколько недель эксплуатации: …аудит доступа и журнал событий…»

**4. Экрана истории звонков нет** ([[05 - Готовность решения - 2026-07-30]] §3.2):
> «Экрана истории звонков в разделе SIP нет, хотя API на стороне ядра существует.»

**5. Аудита открытия двери нет** (прямое следствие) — сам HTTP-unlock не реализован (есть только DTMF в звонке), и DTMF-открытие **не попадает** в единый журнал как событие безопасности. См. [[03 - Открытие двери - DTMF и HTTP-unlock]], раздел «Обязательство по аудиту (§15)».

**6. Идемпотентности, correlation ID, явного результата нет.** Антипаттерн (концепция §2.3):
> `POST /api/call/initiate` — заготовка, которая логирует запрос и возвращает success, ничего не отправив, повторять нельзя.

Сквозной correlation ID по `Call-ID` — это **рекомендация**, не реализовано ([[06 - Устройство SIPManager]]):
> «Добавить observability по call-id: единый correlation ID от SIP `Call-ID` через Kamailio logs, SIPManager logs, push logs и UI events.»

**7. Транзакционной целостности и сверки двух БД нет** ([[06 - Устройство SIPManager]]):
> «Нет транзакционной целостности между SIPManager и Kamailio. Локальная SQL-транзакция SIPManager не покрывает внешние HTTP-вызовы.»

---

## Характер готовности (§4 документа готовности)

Готовность **асимметрична, причём в неудобную сторону**: всё зрелое видно в демонстрации, всё незрелое — не видно. Звонок доходит и картинка появляется, поэтому со стороны кажется, что осталась косметика. Аудит же проявится **только на реальном доме и только через несколько недель эксплуатации**.

---

## Объём закрытия

Аудит и журнал событий — обязательная работа **Этапа 1 пилота** (концепция, Этап 1):
> «…событийный канал для UI (WebSocket/SSE) и история звонков, идемпотентность и сверка провижининга…»

Объём событийного канала — 2–3 ЧМ ([[01 - Выбор базовой архитектуры - платформа или надстройка над VMS]] §16):
> «Событийный канал для UI (WebSocket/SSE нет, только REST) — На нём держатся дашборд, журнал и «активные вызовы» — 2–3 ЧМ.»

## Итог по уровням аудита

| Уровень аудита | Статус |
|---|---|
| SIP CDR (Kamailio `acc`) | ✅ Есть, но «сырые» SIP-события |
| Триггер push (webhook `/calls`) | ✅ Есть, но не журнал |
| API истории звонков | ⚠️ Возможно есть, экрана нет |
| **Единый журнал безопасности** (§15) | ❌ Нет |
| **Событийный канал UI (WebSocket/SSE)** | ❌ Нет вовсе |
| **Экран истории звонков** | ❌ Нет |
| **Аудит открытия двери** (DTMF/HTTP-unlock) | ❌ Нет |
| **Идемпотентность / correlation ID / явный результат** | ❌ Нет (антипаттерн `POST /api/call/initiate`) |
| **Сверка/консистентность двух БД** | ❌ Нет |

**Итог:** на сегодня есть только SIP-accounting в Kamailio (`acc`) и webhook для push. Единого журнала, событийного канала, экрана истории, аудита доступа и открытия двери, идемпотентности и correlation ID — нет. Всё это в объёме Этапа 1 пилота.
