# Прототип: настройка SIP (WEBUI)

Поведенческий прототип экрана настройки SIP-домофонии для облачной системы управления МКД.
Один самодостаточный файл `index.html` — открывается в браузере двойным щелчком,
сервер и сборка не нужны.

- **Статус:** 🟡 черновик, обсуждается
- **Обновлён:** 2026-09-24
- **Домен:** SIPManager + Kamailio, раздел «Настройка SIP» в кабинете администратора
- **Опорные документы:** `40 - Прототипы SIP/06 - Устройство SIPManager`,
  `00 - ТЗ и Концепция/02 - Концепция интегрированной цифровой экосистемы управления МКД (v2)`

## Зачем он нужен

Прототип нужен не для оценки дизайна, а для проверки **поведения**: как администратор
находит нужный объект среди тысяч квартир, как связывает панели с квартирами, что
происходит при удалении того, что уже уехало в Kamailio. Все спорные места домена
разрешены в коде явно — прототип служит исполняемым уточнением к документам.

Он не заменяет ТЗ: если поведение прототипа и текст документа расходятся, побеждает
документ, а расхождение фиксируется в `CHANGELOG.md`.

## Как открыть

Двойной щелчок по `index.html` в любом современном браузере (Chrome, Firefox, Edge, Safari).

Шрифты `Inter` и `Material Symbols Outlined` подключены с `fonts.googleapis.com`, поэтому
при первом открытии нужен интернет. Без сети текст останется читаемым, но иконки
покажутся словами (`apartment`, `dialpad`) — это ожидаемо и на логику не влияет.

Состояние **не сохраняется**: страница всегда открывается с демо-данными заново
(флаг `PERSIST = false` в скрипте). Это сделано намеренно, чтобы демонстрация была
воспроизводимой.

## Доменная модель

Страна одна — РФ, поэтому в дереве её нет, адрес начинается с региона:

```
region (область) → city (город/село) → complex (ЖК) → house (дом)
  → entrance (подъезд) → floor (этаж) → flat (квартира) → account (SIP-аккаунт)
panel (вызывная панель) — крепится к территории ЖК, дому или подъезду
bindings — сквозная связка «панель ↔ квартира», задаётся с любой из сторон
```

ЖК — единица продажи и арендатор: договор, тариф, лимиты и срок подписки живут на нём,
а домов внутри может быть сколько угодно. Один жилец может владеть квартирами в разных
домах, поэтому email уникален только внутри квартиры, а не в установке.

## Какие решения прототип фиксирует

| Решение | Как выражено в UI |
|---|---|
| Статус регистрации SIP — только для чтения | Тумблеров нет, есть кнопка «Проверить статус»; источник истины — Kamailio |
| Realm единый и не редактируется | Поле показано в шапке, в карточках его нет |
| Учётку блокируют, а не «выключают регистрацию» | Переключатель блокировки → `subscriber/delete` + `subscriber/create` при разблокировке |
| Удаление, уходящее в Kamailio, не отменяется через undo | Отложенная фиксация: объект помечен, идёт отсчёт, до конца отсчёта можно отменить |
| Undo остаётся только для локальных правок | Связки панель ↔ квартира, переименования |
| SIP-номер и email валидируются на клиенте | Формат и уникальность проверяются до отправки |
| ЖК как арендатор | Карточка ЖК: договор, тариф, статус и срок подписки, лимиты и их расход |
| Лимиты подписки соблюдаются в UI | Создание квартиры или панели блокируется при исчерпании лимита |

## Оформление: схема ONE PSIM

С 2026-09-24 прототип оформлен по дизайн-схеме ONE PSIM (`ONE.PSIM.PrototypeKit`,
правила `docs/RESTYLE-RULES.md`). Поведение не менялось: все проверки `tests/run.js`
проходят до и после.

Как сделано:

- Файл остался самодостаточным. Вместо подключения `bridge.css` токены
  (`src/theme/one-psim.css`) и базовые стили элементов (`src/theme/native.css`)
  встроены в начало `<style>`. При обновлении кита их нужно перенести вручную.
- Своих переменных у прототипа не было, поэтому цвета переписаны на токены прямо в
  правилах, по роли элемента, а не по совпадению hex (§0.2–0.3). Жёстких цветов в
  CSS и скрипте не осталось.
- Поля: рамка 1px, focus — ореол 2px и рамка `editor-border-focus`; кнопки, строки и
  вкладки — кольцо 2px (§2.5–2.6). Кнопки переведены на лестницы primary / secondary /
  subtle (§2.8): ховер не меняет цвет подписи и рамки, подъём и свечение убраны.
- Выбор в дереве и списках — только фоном (§2.3), выбранный пункт выпадающего
  списка — заливка `accent` без галочки (§2.9), строки меню 32px (§2.9a).
- Знак бренда — знак ONE цвета `fg-subtle` (D-023).
- Типы узлов дерева различаются цветами палитры, которые не совпадают со статусами
  (D-039): регион и город — `fg-muted`, ЖК и дом — `accent-indicator`, подъезд и
  аккаунт — `palette-teal`, этаж — `fg-subtle`, квартира — `palette-purple`,
  панель — `palette-magenta`.

Собственные решения (не из правил кита):

| Решение | Причина |
|---|---|
| Добавлена кнопка темы в шапке (`#themeBtn`, иконка луны / солнца) | В ките две темы, а в прототипе переключателя не было; без него тёмную тему не проверить |
| Выбранная тема запоминается в `localStorage` (`sip-theme`), хотя `PERSIST = false` | Тема — настройка просмотра, а не демо-данные; воспроизводимость демонстрации не страдает |
| Группа «Панели» в дереве оставлена капсом | Это подзаголовок группы в списке — overline капсом разрешён (`MuiListSubheader`), запрет §2.2b касается заголовков разделов |
| Тост инвертирован: фон `fg`, текст `surface`, действие `accent-soft` | В ките нет токенов snackbar; так он читается в обеих темах |
| Переключатель блокировки учётки — тройки success / danger | Это кнопка-состояние, а не Switch; правил для неё в ките нет |
| Опасные кнопки (`.btn-danger`, удаление в модалках) — `palette-red` с шагом ховера | По D-012 / D-022 |

Пробелы в правилах кита, по которым нужен ответ владельца схемы:

- чипы (`.pending-chip`, `.node-chip`) — сейчас фон `warning` через `color-mix` 28%;
- кнопки со статусом success / danger (переключатель блокировки);
- опасный пункт контекстного меню и кнопки действий в строке списка;
- обёртки полей с `:focus-within` (`.cfg-field`, `.scope-field` в шапке) — ореол
  нарисован на обёртке, а не на самом `<input>`;
- тост / snackbar;
- иконочные subtle-кнопки: у нас иконка `fg-muted`, в ките цвет не задан.

## Что осознанно вне области

- Нет бэкенда: все данные в памяти страницы, провижининг Kamailio показан как список
  команд, а не выполняется.
- Нет авторизации и ролей — администратор облака и администратор одного ЖК не различаются
  (решено, что для прототипа это не нужно; переключатель ЖК заменяет разделение прав).
- Нет реального SIP-трафика, звонков и push.
- Нет серверной пагинации: демо-данные подобраны так, чтобы дерево оставалось тяжёлым,
  но браузер справлялся.

## Поведенческие проверки

Что именно прототип делает — списком в [`tests/checklist.md`](tests/checklist.md):
212 проверок в 29 разделах, снимок на 2026-08-07. Этот файл читается без всяких
инструментов, и именно он передаётся разработчикам как приёмочные критерии.

Список получен прогоном `tests/run.js`: скрипт открывает `index.html` в jsdom и
нажимает на элементы так же, как это делал бы администратор — проверяется поведение,
а не вид. Прогонять его нужно только после правок `index.html`, и лучше вне хранилища,
чтобы зависимости не попадали в синхронизацию Яндекс.Диска:

```powershell
# один раз: рабочая папка вне хранилища
mkdir C:\dev\sipcheck; cd C:\dev\sipcheck; npm i jsdom

# каждый прогон: копируем скрипт и передаём ему путь к прототипу
copy "D:\...\_prototypes\sip-setup\tests\run.js" .
node run.js "D:\...\_prototypes\sip-setup\index.html"
```

Каждая проверка печатает `ok` или `FAIL`; ненулевой код возврата означает, что
поведение разошлось с ожидаемым. После прогона обновите `tests/checklist.md`, а если
поведение изменено намеренно — ожидания в `tests/run.js` и запись в `CHANGELOG.md`.
