## 1. Что фактически подтверждено

На стенде `sip-test1` пройден полный путь без разрывов:

```
настройка в облачном UI → выдача SIP-аккаунтов → регистрация iOS и Android
  → входящий вызов с панели Beward и с softphone → VoIP push из фона
  → ответ с видео и звуком → открытие двери DTMF
```

Это подтверждено с трёх сторон независимо: со стороны облака ([[04 - Состояние интеграции облака и sipmanager]]), со стороны обоих мобильных клиентов ([[01 - Состояние iOS прототипа]], [[02 - Состояние Android прототипа]]) и со стороны SIP-сервера ([[03 - Состояние Kamailio]]).

Содержательный итог: самая рискованная связка продукта — «панель → облако → push → телефон → медиа» — перестала быть гипотезой. Провижининг, маршрутизация SIP, push и мобильный приём вызова работают, и проектировать их заново не требуется.

## 2. Готовность по компонентам

| Компонент | Состояние |
|---|---|
| Облачное ядро (`backend` + `sipmanager` + Postgres) | Работает на стенде, ветка `feature/sipmanager_microservice` |
| SIP-сервер (Kamailio 5.7.6 + RTPEngine) | Работает; без TLS/SRTP, один узел, без HA |
| Push-шлюз (APNS VoIP + FCM high-priority) | Работает; веерная рассылка на все устройства аккаунта |
| iOS-клиент (ITV Intercom, Linphone 5.4.88) | Прототип; путь push→CallKit не доведён |
| Android (`android-intercom` + `domofon`) | Прототип; cold-start и живучесть процесса не закрыты |
| Cloud UI, раздел SIP | CRUD дерева, панелей, аккаунтов, share, online-статус |
| Открытие двери вне звонка (REST unlock), привязка RTSP | Отсутствует полностью |
| Событийный канал для UI (WebSocket/SSE), call control | Отсутствует полностью |
| Локальный резервный SIP-контур | Не начат |
| Плагинная платформа (`psim-sdk`) | TRL 3–4, pre-alpha |
| Видеомодуль, СКУД/ОПС, SCADA, паркинг | Не начаты (расширенная конфигурация) |

**По шкале TRL:** ядро и мобильные клиенты — порядка **TRL 5**: компоненты проверены в релевантной среде и на реальной панели, но не в операционной — стенд один, реального дома нет, нагрузочных замеров нет. Оценка **TRL 3–4** для `psim-sdk` взята из собственного разбора проекта ([[psim-sdk-comprehensive-analysis]] §4), а не выведена здесь.

## 3. Что блокирует пилот на реальном доме

### 3.1. Мобильная доставка вызова — главный риск

**iOS** ([[01 - Состояние iOS прототипа]]):

- в `VoipPushLogger.didReceiveIncomingPushWith` payload только логируется, `completion()` не вызывается;
- CallKit репортится на приход SIP INVITE, а не на момент push — прямое расхождение с VoIP-политикой Apple для iOS 13+, то есть риск не косметический, а «система задушит приложение»;
- файла entitlements у `IntercomApp` в дереве нет;
- `core.processPushNotification` / полноценный push-only mode не доведены;
- «получить аккаунт из облака» — disabled TODO.

**Android** ([[02 - Состояние Android прототипа]]):

- push сам по себе не стартует `SipService` и не делает re-REGISTER — он показывает уведомление;
- `SipService` не foreground service, процесс может быть убит ОС;
- в манифесте проверенных версий нет `USE_FULL_SCREEN_INTENT`, `FOREGROUND_SERVICE`, `WAKE_LOCK`;
- Telecom `ConnectionService` / системный UI звонка — в основном stub;
- возможный mismatch ключей payload (`caller` / `type` против `sipNumber` / `callerNumber`);
- баг UI: в `CallingView` кнопка Accept доступна только для `IncomingReceived || Idle`, но не для `IncomingEarlyMedia`, поэтому после early media она может пропасть.

Ключевая оговорка из документа [[02 - Состояние Android прототипа]] звучит буквально так: работает «когда процесс жив и зарегистрирован». Именно это и есть разница между демонстрацией и пилотом.

### 3.2. Функции базовой домофонии, которых нет

- Открытие двери **вне звонка** (HTTP/REST unlock) отсутствует — есть только DTMF внутри звонка.
- Привязки RTSP-камеры панели нет.
- Экрана истории звонков в разделе SIP нет, хотя API на стороне ядра существует.
- Кнопки «открыть дверь» в UI нет.

Все четыре пункта относятся к **базовой** конфигурации, то есть к тому, что продаётся без видеоплатформы.

### 3.3. Инфраструктура ядра

- **Событийного канала для UI нет вовсе** — дашборд, журнал и «активные вызовы» опираются на несуществующую часть.
- **Консистентность двух независимых БД** (`sipmanager` и Kamailio) не обеспечена: нет транзакции, outbox, идемпотентности, периодической сверки.
- **Промышленных манифестов развёртывания не найдено, HA нет** — контур Kamailio единственный.
- **Управляющий API Kamailio** живёт в `kamailio.cfg` на regex-разборе JSON и строковом SQL; порт `8080` нельзя публиковать наружу.
- **TLS-транспорт SIP не поднят**, медиа идёт RTP/AVP через релей.
- **RTP-диапазон `10000–10100`** даёт порядка 12–25 видеовызовов вместо целевых ≥ 50.

## 4. Главное про характер этой готовности

Готовность **асимметрична, причём в неудобную сторону**: всё зрелое видно в демонстрации, всё незрелое — не видно. Звонок доходит и картинка появляется, поэтому со стороны кажется, что осталась косметика. А не сделано именно то, что проявляется только на реальном доме и только через несколько недель эксплуатации:

- доставка вызова после cold start и после суток в фоне;
- аудит доступа и журнал событий;
- поведение при обрыве WAN;
- расхождение двух баз на сотнях аккаунтов;
- отказ единственного узла Kamailio.

**Ограничение объёма проверки.** Контур подтверждён на одном стенде, одной моделью панели (Beward) плюс softphone-имитация. Матрицы совместимости панелей, нагрузочных замеров и мониторинга нет.

## 5. Ориентиры по срокам

По [[04 - Оценка трудозатрат - МКД]]:

| Рубеж | Состояние | Оценка |
|---|---|---|
| Демонстрация заказчику | Готово сейчас | — |
| Пилот базовой конфигурации на одном доме | Не готово | ~22–31 ЧМ, ~5–6 мес, команда 7–8 чел. |
| Промышленная версия под тираж | Не готово | ~41–63 ЧМ, ~12–16 мес, команда ~10 чел. |

**Формулировка, наиболее точно описывающая статус:** ядро домофонии реализовано и проверено сквозным тестом, поэтому пилот начинается не с нуля — но промышленная зрелость (доставка вызова, события, консистентность, HA, локальный резерв) предстоит целиком.
