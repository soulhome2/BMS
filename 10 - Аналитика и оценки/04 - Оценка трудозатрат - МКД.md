
> Приложение к [[02 - Концепция интегрированной цифровой экосистемы управления МКД (v2)]].
> Тип: укрупнённая экспертная оценка (ROM, ±30–40%). Уточняется после Этапа 0 (проектирование).

---

## 0. Главное допущение

**Облачное ядро не разрабатывается с нуля — оно реализовано и работает на стенде.** Авторизация и права, дерево адресов/панелей/аккаунтов, провижининг SIP, SIP-сервер (Kamailio 5.7.6 + RTPEngine), push-шлюз APNS/FCM и раздел SIP в cloud UI проверены на стенде sip-test1 сквозным путём «настройка в UI → аккаунты → регистрация → вызов с панели Beward → push из фона → ответ с видео и звуком» ([[04 - Состояние интеграции облака и sipmanager]], [[03 - Состояние Kamailio]], [[01 - Состояние iOS прототипа]], [[02 - Состояние Android прототипа]]).

Отсюда два следствия, которые сильно влияют на объём:

1. **«Мост в облако» не проектируется.** Трансляцию SIP-событий, провижининг учёток и push выполняет существующий `sipmanager`; отдельный «SIP-коннектор» как разрабатываемый микросервис не нужен.
2. **WebRTC не на критическом пути.** Ответ на вызов из браузера не входит в этап 1, значит медиасервер SIP↔WebRTC, coturn и связанная дефицитная экспертиза не блокируют пилот.

**При этом готовность ядра — стендовая, а не промышленная**, и часть механизмов отсутствует ([[06 - Устройство SIPManager]]). В объём базовой конфигурации входят четыре позиции, которые легко упустить именно потому, что домофония «уже работает»:

- **событийного канала для UI нет** (WebSocket/SSE в `sipmanager` отсутствует, только REST) — а на нём держатся дашборд, журнал и «активные вызовы»;
- **call control из UI отсутствует** (нет исходящего INVITE, BYE/CANCEL; `POST /api/call/initiate` — заготовка без отправки SIP) — для этапа 1 не блокер, но это отдельная работа;
- **консистентность провижининга не обеспечена** (две БД, нет транзакции, outbox, идемпотентности, сверки);
- **промышленной оркестрации и HA нет** (ни Helm/K8s, ни systemd, ни terraform; один контур Kamailio).

**Видеоплатформа — опциональный модуль.** Видеозахват, аналитика, архив, ACFA (СКУД/ОПС) и Авто-Интеллект (LPR) берутся готовыми и не разрабатываются, но это трудозатраты **расширенной конфигурации**, а не фундамент проекта. Базовая конфигурация оценивается и сдаётся без них.

## 2. Трудозатраты по компонентам (человеко-месяцы)

Колонка «Конфиг.»: **Б** — базовая (нужна для пилота домофонии), **Р** — расширенная (видео и инженерия), **О** — общая.

| Компонент | Конфиг. | ЧМ (min–max) | Ключевой риск |
|---|---|---|---|
| Доводка облачного SIP-контура: TLS-транспорт и SRTP, расширение RTP-диапазона, эксплуатационная обвязка | Б | 1–2 | Низкий — контур работает |
| **Локальный резервный SIP-контур на объекте** | Б | 2–3 | Высокий — синхронизация учётных данных и переключение без потери вызова |
| Доработка ядра/`sipmanager`: история звонков, панель как устройство, привязка RTSP и способа `unlock` | Б | 2–3 | Средний |
| **Событийный канал ядра для UI** (WebSocket/SSE, события вызова и доступа, correlation ID по `Call-ID`) + потребление в UI | Б | 2–3 | Средний — в ядре нет вообще, от него зависят дашборд, журнал, активные вызовы |
| **Консистентность провижининга**: идемпотентность, outbox с повторами, reconciliation, метрика расхождений | Б | 1–2 | Средний — без этого «аккаунт есть, регистрации нет» на больших домах |
| **Промышленная оркестрация и HA ядра** + вынос управляющего API из `kamailio.cfg` | Б | 2–3 | Высокий — сейчас единая точка отказа, манифестов нет |
| **Драйверы вызывных панелей** `unlock` (HTTP/CGI) + `camera` (RTSP), по моделям | Б | 2–3 | Средний — URL unlock зависит от модели и прошивки |
| Мобильные приложения: доведение прототипов iOS+Android до продакшена (PushKit→CallKit, cold start, foreground service, UX) | Б | 4–6 | **Высокий — главный риск проекта** |
| Плагинный фреймворк ядра + плагин SCADA | Р | 4–6 | Средний |
| ОПС/СКУД: glue к ACFA + прямые драйверы приборов для базовой конфигурации | Р | 3–5 | Средний — прямые драйверы существенно дороже готовых модулей ACFA |
| Веб-UI поверх существующего cloud UI (дашборд, планы, журнал, сценарии) | О | 5–8 | Средний — конструктор сценариев трудоёмок |
| Адаптер видеомодуля (RTSP-уровень + расширенный API линейки ITV) | Р | 2–3 | Средний — зависит от документации SDK, но это опция |
| QA / интеграционное тестирование / совместимость железа | О | 4–6 | Средний — нужен парк оборудования |
| PM / аналитика / UX-дизайн | О | 4–6 | — |
| DevOps / CI / инфраструктура / HA / мониторинг | О | 3–4 | Средний |
| **Итого полный охват** | | **~41–63 ЧМ** | |
| *в том числе:* **базовая конфигурация (пилот домофонии)** с долей QA/PM/DevOps | Б | **~22–31 ЧМ** | |
| **Отложено:** медиасервер SIP↔WebRTC + coturn + браузерный ответ | — | 3–4 (вне этапа 1) | Высокий, но не блокирующий |
| **Отложено:** call control из UI (исходящий вызов, hangup, приоритетный дозвон) | — | 2–3 (вне этапа 1) | Средний |

**Как читать эти цифры.** Базовая конфигурация (~22–31 ЧМ) — это то, что нужно для сдачи домофонии на реальном доме: доводка мобильных клиентов, драйверы панелей, события для UI, локальный резерв и промышленная обвязка ядра. Экономия относительно разработки «с нуля» возникает не в интерфейсе и не в мобильном приложении, а в ядре: провижининг, маршрутизация SIP, push и приём вызова на мобильном уже работают, и их не нужно ни проектировать, ни писать.

Обратная сторона: именно из-за того, что домофония «уже звонит», легко недооценить обвязку — события реального времени, консистентность двух баз и отсутствие HA не видны в демонстрации, но обязательны для сдачи по NFR.

## 3.1. Требуемый уровень команды

Команда должна быть **преимущественно middle+ / senior**, а не junior. В проекте много «тонких» инженерных зон (WebRTC/SIP, интеграция с чужим SDK, отказоустойчивость, VoIP push), где ошибки junior-уровня стоят срыва сроков.

| Роль | Уровень | Почему именно так |
|---|---|---|
| Tech Lead / архитектор | Senior / Lead (8+ лет) | Держит архитектуру ядра и границу с опциональными модулями, снимает риски |
| VoIP / SIP-инженер | Senior (обязательно) | Kamailio/RTPEngine, early media, кодеки и **локальный резерв на объекте** — junior здесь провалит проект. WebRTC/TURN понадобится только на отложенном этапе |
| Mobile (iOS/Android) | Senior с реальным опытом VoIP push | **Критический путь этапа 1.** Прототипы есть, но незакрыты именно самые тонкие места: PushKit→CallKit по политике Apple, cold-start re-REGISTER, foreground service |
| Backend (доработка ядра, плагины, драйверы) | 1 Senior + 1–2 Middle | Senior задаёт контракт плагина и модель устройства «панель», middle пишут драйверы под присмотром |
| Frontend | Middle → Middle+ | Расширение cloud UI, WebSocket; конструктор сценариев требует крепкого middle+ |
| DevOps | Middle+ / Senior | Docker, HA SIP/медиа, порты RTP, узлы локального резерва, CI — нужен опыт с сетевой инфраструктурой |
| QA | Middle (+ желательно 1 с автотестами) | Интеграционное тестирование, работа с железом, проверка сценариев отказа WAN |
| PM / системный аналитик | Middle+ / Senior | Управление зависимостями, работа с заказчиком (УК/застройщик), NFR |
| UX/UI-дизайнер | Middle (part-time) | Дашборд, планы этажей, мобильные экраны |

**Ключевой принцип.** Проект «вытягивают» 3 сильных человека, без которых сроки поплывут:
1. Senior mobile с реальным опытом VoIP push — роль №1: домофония является базовой функцией продукта, а её воспринимаемое качество целиком упирается в надёжность доставки вызова;
2. VoIP/SIP-инженер (Kamailio/RTPEngine + локальный резерв);
3. Архитектор / Tech Lead.

Остальные могут быть middle — но обязательно под руководством senior'ов. Полностью junior-команда не подходит: слишком много специфичной телеком-экспертизы.

**Влияние уровня на оценку:**
- **Сильная профильная команда** (senior с опытом SIP и мобильного VoIP push) → нижняя граница (~41 ЧМ, ~12 мес).
- **Средняя команда** (middle + пара senior) → верхняя граница (~63 ЧМ, ~16 мес) + буфер.
- **Слабая/junior команда без телеком-опыта** → оценка перестаёт работать: риск многократного превышения сроков на мобильном push и локальном резерве.

> Практический вывод: экономить лучше на количестве middle-разработчиков, но **не экономить на senior mobile с опытом VoIP push, VoIP/SIP-инженере и архитекторе** — это узкое место всего проекта.

Этап 0 короткий, потому что ключевые архитектурные вопросы (какой SIP-сервер, как устроен провижининг, нужен ли WebRTC на старте, как открывается дверь) уже закрыты прототипами и документами [[05 - Разбор непонятных моментов в документах]] и [[06 - Устройство SIPManager]]. Остаётся спроектировать контракт событий, схему консистентности, локальный резерв и оркестрацию.

**Итоговые ориентиры:**
- **Работающий пилот домофонии** (базовая конфигурация, без видео): **~5–6 месяцев** календарно.
- **Пилот с видеомодулем**: **~7–9 месяцев**.
- **Промышленная версия под тираж**: **~12–16 месяцев** календарно.
- Суммарно **~41–63 человеко-месяца** при команде **~10 человек**; из них базовая конфигурация — **~22–31 ЧМ** при команде ~7–8 человек.

## 5. Факторы, сильнее всего влияющие на оценку

1. **VoIP push на iOS/Android** — главный риск этапа 1. Прототипы работают на стенде, но незакрыты именно требовательные места: CallKit в момент push по политике Apple, cold-start re-REGISTER, живучесть процесса на Android.
2. **Локальный резервный SIP-контур** — работа без готового аналога внутри проекта. Стоимость зависит от выбранной схемы (полноценный узел на объекте против упрощённого режима панели) и от требования «переключение без потери активного вызова».
3. **Парк оборудования и разнообразие панелей** — `unlock` реализуется драйвером под модель и прошивку, «общего SIP INFO» не существует. Чем шире матрица поддерживаемых панелей, тем дороже; без физического железа интеграционное тестирование тормозит.
4. **Промышленная зрелость ядра** — контур один, HA и production-манифестов нет, управляющий API живёт в `kamailio.cfg` на regex-разборе JSON и строковом SQL. Пока это не закрыто, «сдать» систему по NFR нельзя, а нагрузочные показатели упираются и в RTP-диапазон `10000–10100` (порядка 12–25 видеовызовов).
5. **Доступность SDK/API видеоплатформы и лицензий ACFA** — риск невысокий: он локализован в опциональном модуле и не блокирует пилот.
6. **Зрелость команды** в SIP и мобильном VoIP — с профильной командой берётся нижняя граница, без неё — верхняя и +буфер.
7. **Объём call control, который потребуют в этап 1** — если нужен исходящий вызов и завершение из интерфейса, добавляются 2–3 ЧМ и решение «кто SIP UA или B2BUA»; если нужен ещё и браузерный ответ — плюс 3–4 ЧМ, дефицитная экспертиза и TURN.
